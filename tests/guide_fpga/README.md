# 屏幕演奏指引 RTL 验证

从工程根目录运行 python tests/guide_fpga/run.py，需要 Icarus Verilog 和 Python 3。脚本同时运行两项回归并保存 results/validation.json。

tb_guide.v 经 guide_transport 的真实 28 字节入口执行 179 条请求，检查返回 CRC16、重复包、事件 CRC32、双银行提交与失败保留、同时和弦、跨轨相同琴键、延音、暂停、前后步进、速度、结束归零、512 事件上限、录音互斥以及两种超时。接收和 ACK 使用独立的间隔及反压。

tb_java_upload.v 直接读取 Android Java 编码器生成的 demo-upload.hex。24 个原始包上传 84 个事件，逐字检查写入银行，随后验证播放、释放与同键重触。返回的 576 字节 TGAK 位于 results/demo-acks.hex，可再送入安卓解码器交叉验证。

播放器保留两组逻辑 512×32 事件银行，但物理上合并为一个 1024×32 RAM，以地址最高位区分银行，再映射为两块原生 1024×16 BSRAM。不能用综合阶段的逻辑 primitive 数量代替实际占用：原来分开的 512×32 SDP 数组在综合报告中也是两块，但 GW5AT-60B 的布局布线会各拆为两块，共占四块。合并方案已经以真实布局布线核对。短包缓存显式指定为寄存器。时间以音频帧节拍计算，正常速度每个 audio_tick 累加 256，到 125000 时推进一个 10 ms 单位，适配 50 MHz / 1024 的实际帧率。

上电默认内置 56 事件、16 秒的白键短句。上传写非活动银行，全部事件和 CRC32 通过后才停止旧曲、切换银行并回到开头。暂停保留当前和弦。新弹的亮度强调最长 150 ms，播放结束清空目标并将进度归零。手动前后步进会重建目标时间的全部活动音，同时区分该时刻新弹音与先前延音。

导入曲目位于 SRAM，断开手机可以继续播放，断电后回到内置短句。预告显示下一事件时间组中的新弹键，下一组只有释放时预告暂时为空。

## 真实 UART 与录音复用回归

从工程根目录执行：

```powershell
python tests/guide_fpga/run_console.py --timeout
```

`tb_console.v` 实例化实际 `bt_console`、自动波特率 `bt_link`、8N1 UART、指引模块和 ADPCM 录音模块。输入逐位驱动，每位 434 个 50 MHz 时钟；输出由独立 UART 接收器逐位采样，校验停止位、每帧长度和 CRC，不从 DUT 内部发送数据线读取结果。

覆盖 `UUUU` 自动波特率训练、`~I` 录音能力查询、`~G` 安全指引能力查询、Android 产生的全部 24 个上传/播放请求，以及录音期间包含 `~S`、`M`、`T`、`U`、`A5` 等字符的完整二进制包。验证该包被整体丢弃，不能误触文本命令、结束录音或改动曲目；随后正常 `~S` 结束录音，`~G` 仍能查询。`--timeout` 另等待真实的 12,500,000 时钟超时，检查未完整接收的被丢弃二进制包不会使通道永久占用。

完整测试约 20.4 M 时钟，结果为 27 个合法 TGAK、4 个音频 DATA 帧、1 个正常结束帧及一条合法 ASCII 状态回复。串行字节实录在 `results/console-timeout-wire.hex`（1024 字节），机器可读结果和源码 SHA256 在 `results/console-timeout-validation.json`；这是 RTL 仿真证据，不替代手机与实板联调。不带 `--timeout` 时省略长等待，保留其余测试。
